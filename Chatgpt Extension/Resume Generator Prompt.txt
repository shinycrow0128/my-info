2. TIMELINE, TENURE, AND SENIORITY MATCH (MANDATORY)
════════════════════════════════════════

This is the #1 failure mode to prevent: early company years must match early-career work.

For EACH company, calculate tenure length from the Temp dates, then cap claim intensity:

| Tenure / career stage | Allowed scope | Forbidden claims |
|-----------------------|---------------|------------------|
| Early companies (oldest 1–2) | Foundations: features, modules, bug fixes, scripts, integrations, learning production systems, contributing under seniors | Sole architect of platform; org-wide strategy; mentoring large teams; inventing company tech direction |
| Middle company | Ownership of a service/module; production incidents; design of a subsystem; some cross-team work | Principal-level portfolio ownership across many domains |
| Latest 1–2 companies | Architecture, leadership, scale, business impact, mentoring, reusable frameworks | Claims impossible for the stated title or short tenure |

Hard rules:
1. Match work sophistication to YEARS in that role and TOTAL career stage.
   - ~1 year early role → contributor/feature depth, not “led enterprise redesign”
   - Multi-year recent senior role → deeper ownership and impact OK
2. Technology must exist during that employment period.
   - No Kubernetes in 2012, no GPT/LLM agents before ~2022–2023, no React Native before it existed, etc.
3. Stack progression must be believable over time.
   - Early roles: fewer tools, simpler systems, smaller scope
   - Later roles: more complexity, scale, leadership — not the same bullet template with bigger adjectives
4. Metrics must fit tenure and title.
   - Do not claim “cut cost 40% company-wide” for a junior 10-month role
   - Prefer team/service/project scope over org-wide miracles for early roles
5. Do not make Company 1 sound like Company 5 with different nouns.
6. Keep employment dates EXACTLY as in Temp DOCX. Never invent overlapping full-time roles.

Before finishing, self-check: “If a recruiter compares title + dates + bullets, does seniority make sense?” If not, rewrite.

════════════════════════════════════════
7. BULLET WRITING RULES
════════════════════════════════════════

Formula (compressed STAR):
[Action verb] + [what you built/changed] + [how it worked / key tech] + [who/what improved] + [credible result]

Each strong bullet should answer:
* What business/problem existed?
* What did the candidate design or build?
* How did it work (brief technical mechanism)?
* Which technologies were used and why they fit?
* What changed (time, errors, throughput, cost, reliability, scale)?

Good:
“Built a Python intake workflow that validated vendor API payloads, queued retries on failure, and cut manual case handling from ~11 minutes to ~3 minutes for ops reviewers.”

Bad:
“Used Python and AWS for automation.”
“Leveraged cutting-edge solutions to drive synergies.”

Metrics rules (IMPORTANT — fraud checkers flag metric-dense resumes):
* Most bullets should have NO before→after number
* Metric budget by career stage:
  - Latest company: at most 1–2 measured bullets
  - Second-latest: at most 1–2 measured bullets
  - Middle: at most 1 measured bullet
  - Early companies: 0–1 measured bullet total (prefer scope words, not dashboards)
* Across the WHOLE resume: ideally 4–7 measured bullets max, not 15+
* Prefer ranges and scoped metrics over fake precision
* Avoid AI-looking round sets: 30%, 50%, 100%, 10x repeated everywhere
* Scope metrics to what that role/tenure could influence
* If a number is not defensible in an interview, use qualitative scope instead
  (“across 8 partner feeds”, “for a 12-person support team”)
* Do NOT put precise before-and-after measurements on almost every position
* Other bullets should describe build/fix/ownership without dashboard math

ANTI-REPEAT RULE (mandatory):
* Never reuse the same benchmark phrasing or near-same numbers across companies
* Each measured bullet must use a DIFFERENT metric family from others already used
* Before writing Company N, list metrics already used in Companies 1..N-1 and ban them
* Do not cycle the same trio (e.g. “11 min → 3 min”, “12–15 → 3–4 defects”, “32% reduce”) on every job
* Change both the number AND the unit/type (time vs volume vs error vs cost vs scale)

Metric family rotation (use sparingly — usually 1 family per company when a metric is used):
1. Latency / response time
2. Throughput / volume
3. Error / defect / failure rate
4. Cycle time / lead time / sprint throughput
5. Manual effort / headcount hours saved
6. Availability / MTTR / incident count
7. Cost / infra spend / token spend
8. Coverage / adoption / integration count
9. Data quality / accuracy / reconciliation
10. Search / query / retrieval quality
11. Build / deploy / CI speed
12. Device / firmware / real-time constraints (embedded only)

8. WRITE LIKE A HUMAN — RESUME-ONLY ANTI-AI RULES
════════════════════════════════════════

Primary goal of this section: the finished resume must read as written by a working engineer,
not by ChatGPT. Optimize against resume-text AI tells (structure, vocabulary, rhythm, metrics).
Do not mention AI, prompts, or detectors in the resume.

Hard requirement: if the draft still looks AI-templated, rewrite before export.

────────────────────────────────────────
8A. BANNED VOCABULARY (never use)
────────────────────────────────────────
spearheaded, leveraged, utilized, orchestrated, facilitated, transformed, revolutionized,
synergy, synergies, robust, seamless, cutting-edge, state-of-the-art, best-in-class,
results-driven, detail-oriented, passionate, proven track record, highly motivated,
dynamic, proactive, innovative solutions, elevate, optimize synergies, drive value,
thought leader, visionary, multifaceted, unwavering, delve, landscape, ecosystem
(unless “ecosystem” is a real product term in the company), “at the intersection of”,
“playbook”, “north star”, “mission-critical” (overused), “end-to-end solutions” as filler

Prefer plain verbs:
built, wrote, fixed, shipped, cut, moved, migrated, tuned, owned, debugged, redesigned,
replaced, measured, rolled out, split, cached, queued, refactored, documented, reviewed

────────────────────────────────────────
8B. BREAK THE TEMPLATE RHYTHM (biggest AI tell)
────────────────────────────────────────
AI resumes use the same skeleton every bullet:
[Verb] + [system] + [tech list] + [metric].

Humans mix bullet TYPES inside each role. For every company, use a mixed set:

Type 1 — Build/ship (what was created)
Type 2 — Fix/incident (what broke and what changed)
Type 3 — Constraint (team size, deadline, legacy limit, traffic spike)
Type 4 — Decision/tradeoff (chose X over Y because …)
Type 5 — Short punch (1 short line, no long clause stack)
Type 6 — Scope line (users, volume, teams) without a fake %

Rules:
* Inside one role, do NOT make every bullet the same length
* Target mix per recent role: ~2 long, ~3 medium, ~1–2 short
* Do not start more than 2 bullets in a role with the same verb
* Do not end every bullet with a percentage
* At least 1 bullet per recent role may have NO metric (still specific)
* Never clone Company 5’s bullet pattern onto Company 1 with different nouns

Good rhythm example (illustrative):
* Built …
* After repeated timeout failures on …, replaced … which cut …
* With a 2-engineer team, …
* Chose Postgres over … because …
* Owned on-call for …

────────────────────────────────────────
8C. SPECIFICITY BEATS POLISH
────────────────────────────────────────
Every role needs lived-in detail that generic AI text usually skips:
* Named internal system/product in plain English (not “various projects”)
* Concrete failure mode or bottleneck (timeouts, poison messages, flaky deploys)
* Who felt the pain (ops, clinicians, warehouse, support, sales ops)
* Tool versions or exact services only when natural (EKS, RDS Postgres, SQS)
* One messy constraint: legacy SOAP feed, no staging data, freeze window, small team

Avoid abstract filler:
Bad: “Improved system performance and reliability across the platform.”
Good: “Cut checkout p95 from ~1.9s to ~700–800ms by adding Redis caching on the inventory read path.”

────────────────────────────────────────
8D. METRICS THAT LOOK HUMAN (AND NOT FABRICATED)
────────────────────────────────────────
* Prefer ranges and uneven numbers: 140–180ms, 8–12 min, 3–4 defects, $11–13k/mo
* Avoid clusters of 10/20/25/30/40/50/100% across the resume
* Most bullets have NO number — measured bullets are the exception
* Do not reuse the same before→after pair on multiple companies
* When unsure, use scope instead of a glamorous %
* Fraud red flag to avoid: almost every position has several precise before/after measurements

────────────────────────────────────────
8E. SUMMARY MUST SOUND HUMAN
────────────────────────────────────────
* 3–5 lines max, specific role + domain + 1 concrete strength
* No adjective stacks (“innovative, passionate, results-driven senior engineer”)
* Bold at most 3–5 keywords, not whole phrases of hype
* Do not mirror the JD sentence-for-sentence

────────────────────────────────────────
8F. JD KEYWORD USE WITHOUT AI / FRAUD OVERFIT
────────────────────────────────────────
* Put must-have terms in Skills + a few bullets in the LATEST 1–2 roles naturally
* Do NOT spread every niche JD keyword across all five employers
* Early/mid roles may use foundation skills only (APIs, SQL, Python, cloud basics)
* Niche stack items from the JD (e.g., Elasticsearch, LangGraph, specific vendor tools)
  belong mainly in recent roles + Skills — not forced into Company 1–3
* Do not paste uncommon JD marketing phrases into every section
* If removing the JD, the resume should still read like a coherent career — not a keyword collage
* Rough guide: tool overlap in Skills is good; “every employer did every JD niche task” is a fraud flag

────────────────────────────────────────
8G. MANDATORY HUMANIZATION PASS (do this last)
────────────────────────────────────────
Before returning the DOCX, run this pass on the full experience section:

1) Highlight all opening verbs → replace repeats
2) Count measured before→after bullets on the whole resume → if more than ~7, strip extras to scope/no-metric
3) If any early company has 2+ precise metrics, remove down to 0–1
4) Check bullet lengths → if all similar, shorten 2 and lengthen 1 per recent role
5) Delete any banned word that slipped in
6) Confirm each company has a distinct project story (not the same automation tale)
7) Confirm niche JD tools are not copy-pasted into every employer
8) Read the latest role aloud mentally: if it sounds like a brochure, rewrite 2 bullets with constraints/tradeoffs
9) Verify DOCX metadata (Subject, empty Comments, Created, Modified, Author) before export
10) Remove all Word comments and clear Properties/Info → Comments before delivery

Self-test questions (all should be YES):
* Could two different engineers have written different sentences here?
* Is there unevenness (short + long bullets)?
* Are there concrete systems and failure modes, not only achievements?
* Would this still look specific if all percentages were removed?

If any answer is NO, rewrite until YES.

Note: No prompt can guarantee a 0 on every AI detector (detectors are noisy on technical writing).
This section targets the tells humans and resume checkers actually use on the document itself.
